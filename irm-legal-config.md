# Section A: IRM Entity & Risk Indicator Setup

Integrated Risk Management (IRM) is leveraged to assess, track, and mitigate facility-level environmental risks. 

## A.1 — Facility ↔ IRM Entity Mapping

* **Configuration Choice**: **Reference Relationship** (Facility table maps to a separate IRM Entity record).
* **Justification**:
  Rather than extending the core `sn_grc_profile` (GRC Profile / Entity) table directly onto the `x_snc_ecosentine_0_facility` table, the Facility table holds a reference field `irm_entity` pointing to `sn_grc_profile`.
  1. **Compliance Separation**: Extends flexibility by keeping custom operational facility data isolated in our application scope while mapping to native GRC classes.
  2. **Entity Class Separation**: Allows facilities to participate in parent-child hierarchy roll-ups (e.g. mapping Facilities to parent Companies/Sectors) inside the native IRM Workbench without corrupting the operational tables.
  3. **Metadata Mapping**: A Business Rule runs on Facility creation to automatically provision a matching Entity (`sn_grc_profile`) record using the GRC Profile Class of "Facility".

## A.2 — Risk Indicator Definition

Risk Indicators monitor specific operational data to flag compliance shifts.

| Property | Configuration Value |
|---|---|
| **Indicator Name** | Facility Environmental Risk Indicator |
| **Source Type** | Script Include |
| **Target Field** | `x_snc_ecosentine_0_facility.risk_score` |
| **Scale** | 0 to 100 |
| **Refresh Frequency** | Event-Driven (Recalculated on updates) & Daily Scheduled Execution |
| **Calculation Source** | `x_snc_ecosentine_0.EcoRiskCalculator` |

* **Collection Logic**: The indicator utilizes the output of the server-side calculator, capturing it directly from the facility table. GRC scheduled collection engines pull this value into `sn_grc_indicator_results` to maintain risk metrics history.

---

## A.3 — Risk Threshold Configuration

The threshold representing critical compliance danger is set at **$\ge$ 80**.

* **GRC Threshold Rule Setup**:
  * Trigger: An Indicator Result is generated where `value >= 80`.
  * Action: The threshold rule automatically initiates two parallel actions:
    1. **SLA Flagging**: Sets the Facility Boolean field `high_risk` to `true`.
    2. **Automation**: Invokes `SF-02` (Risk Recalculation Subflow) which dispatches the Critical alert notification to the `EcoSentinel — Compliance Officers` group and flags the facility record in dashboard list views.
* **UI Feedback**: Visual policies color-code the risk dashboard indicators based on this threshold value.

# Section B: Legal Service Delivery (LSD) Configuration

ServiceNow's Legal Service Delivery (LSD) plugin provides matter management, case lifecycles, and legal workspaces.

## B.1 — Case Type Configuration

* **Configuration Choice**: **New Custom Case Type** (`x_snc_ecosentine_0_legal_case` extending `sn_legal_case`).
* **Justification**:
  Extending the native `sn_legal_case` leverages OOB LSD workspaces, document templates, legal holds, and matter routing while keeping environmental fields (e.g. violation type, source inspection, penalty type) encapsulated inside the EcoSentinel scope.

---

## B.2 — Field Mapping & Narrative Construction

The legal case record is auto-generated by Flow `FL-05` when an inspection confirms a violation. The narrative is subsequently written by `FL-07` using inputs from the **Legal Case Summary Agent**.

| Source Record | Source Field | Target LSD Case Field | Purpose |
|---|---|---|---|
| `x_snc_ecosentine_0_complaint` | `sys_id` | `source_complaint` | Establishes source intake trace. |
| `x_snc_ecosentine_0_inspection` | `sys_id` | `source_inspection` | Establishes field investigation trace. |
| `x_snc_ecosentine_0_facility` | `sys_id` | `violating_facility` | Identifies legal entity to prosecute. |
| `x_snc_ecosentine_0_inspection` | `violation_type` | `violation_type` | Categorises legal offence. |
| AI Summary Agent | `ai_output` | `case_narrative` | Structured brief detailing the prosecution case. |

---

## B.3 — Case States & Lifecycle Sync

The LSD case lifecycle manages enforcement processing.

```
[1] Case Opened ➔ [2] Evidence Compiled ➔ [3] Notice Issued ➔ [4] Penalty Assessed ➔ [5] Under Appeal ➔ [6] Resolved
```

* **Complaint Status Sync**:
  * When Case state enters **`1` (Case Opened)**: Parent Complaint state is updated to `6` (Action Taken) and `violation_confirmed` is marked `true`.
  * When Case state enters **`6` (Resolved)**: `FL-11: Legal Case Resolution Sync` updates the Parent Complaint state to `8` (Closed) with resolution details mapped to the citizen-facing comments.

## B.4 — Exact Table Reference Fields
The tables maintain strict relationships as outlined in `tables.md`:

```
x_snc_ecosentine_0_complaint (linked_facility) ────► x_snc_ecosentine_0_facility
      ▲
      │ (parent_complaint)
x_snc_ecosentine_0_inspection (inspected_facility) ──► x_snc_ecosentine_0_facility
      ▲
      │ (source_inspection)
x_snc_ecosentine_0_legal_case (violating_facility) ──► x_snc_ecosentine_0_facility
```

* **Traceability Links**: `x_snc_ecosentine_0_legal_case` contains explicit references `source_complaint` (Reference $\rightarrow$ `x_snc_ecosentine_0_complaint`) and `source_inspection` (Reference $\rightarrow$ `x_snc_ecosentine_0_inspection`) to complete the three-way evidence chain.

## B.5 — Security & Access Control

* **Write Access**: Restricted to users holding the `x_snc_ecosentine_0.legal_handler` role (assigned to the `EcoSentinel — Legal Prosecution Team` group) or the `x_snc_ecosentine_0.admin` role.
* **Read Access**:
  * `x_snc_ecosentine_0.officer` (Compliance Officers) has read-only access to Legal Cases for status tracking.
  * `x_snc_ecosentine_0.inspector` (Field Inspectors) has **no read access** to Legal Cases to prevent security exposure regarding ongoing prosecutions.
* **Field Restrictions**: The `case_narrative` field is locked (read-only) once it passes the "Notice Issued" state to maintain the integrity of prosecution records.
