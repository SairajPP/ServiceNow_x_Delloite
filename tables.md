## Naming Convention Note

In a **scoped application**, ServiceNow automatically prefixes every custom table and field with the scope namespace (e.g. `x_eco_complaint`, `x_eco_complaint.ai_severity`). The `u_` prefix is only used for custom fields added to **global-scope** or **OOB tables**. Throughout this document:

- **Table names** use the format `x_eco_<table>`.
- **Custom field internal names** are shown *without* the scope prefix for readability (e.g. `ai_severity`). ServiceNow will store them as `x_eco_complaint.ai_severity` automatically.
- **Inherited fields** from parent tables (e.g. `task.number`, `task.state`) are listed separately to show what you get for free.

## Roles & Access Control

EcoSentinel does **not** need a custom user table. All users (inspectors, officers, admins) are standard `sys_user` records. Access is governed by **scoped application roles** and ACLs.

| Role Internal Name | Label | Description | Typical User |
|---|---|---|---|
| `x_eco.citizen` | Citizen | *Optional — only needed if you gate Service Portal access. For the hackathon, citizens submit anonymously via Record Producer; tracking is by complaint number + email.* | Public portal user |
| `x_eco.inspector` | Field Inspector | Can view/update assigned inspections, create findings, upload photos via Now Mobile. Cannot view unassigned complaints. | Field staff |
| `x_eco.officer` | Compliance Officer | Can view all complaints, inspections, legal cases. Can manually override AI severity. Can trigger re-inspections. | Back-office staff |
| `x_eco.admin` | EcoSentinel Admin | Full CRUD on all EcoSentinel tables. Can configure flows, manage facilities, view AI Control Tower logs. | App administrator |

### Citizen Authentication Strategy

Citizens submit complaints **without logging in**. Identification is handled by:
- A unique auto-generated **Complaint Number** (e.g. `ES-2026-0001`) returned on submission.
- An **optional email** and **optional phone** captured on the form — used for status-update notifications and for the citizen tracker lookup page.
- The Service Portal "Track My Complaint" page accepts `complaint number + email` as a lightweight authentication pair.
- *Future*: If citizen accounts are needed later, create `sys_user` records with the `x_eco.citizen` role and link them via the `opened_by` field inherited from Task.

## Entity Relationship Summary

```
CITIZEN (anonymous, no sys_user required)
  |
  | submits via Service Portal
  v
COMPLAINT (x_eco_complaint) --- extends Task
  |
  |---> FACILITY (x_eco_facility)           [complaint.linked_facility -> facility]
  |       Complaint is geo-matched to a known facility.
  |       Multiple complaints can reference the same facility.
  |       Facility's risk_score, violations_12m, and complaints_90d
  |       are recalculated whenever a complaint or inspection closes.
  |
  |---> ENVIRONMENTAL SNAPSHOT (x_eco_env_snapshot)  [1:1, snapshot.parent_complaint -> complaint]
  |       Exactly one snapshot per complaint, frozen at AI classification time.
  |
  |---> AGENT DECISION LOG (x_eco_agent_log)         [1:many, log.linked_record -> complaint sys_id]
  |       Multiple agent decisions per complaint (Triage, Vision, Fusion).
  |       Also linked to Inspections and Legal Cases for their respective agents.
  |
  +---> INSPECTION (x_eco_inspection) --- extends Task  [1:1, inspection.parent_complaint -> complaint]
          One inspection per complaint (for hackathon scope).
          |
          |---> INSPECTION FINDING (x_eco_finding)   [1:many, finding.parent_inspection -> inspection]
          |       Multiple findings (photos, measurements, observations) per inspection.
          |
          |---> AGENT DECISION LOG (x_eco_agent_log) [1:many, log.linked_record -> inspection sys_id]
          |       Inspection Report Agent decisions logged here.
          |
          +---> LEGAL CASE (x_eco_legal_case)        [1:1, inspection.linked_legal_case -> legal_case]
                  Created only when violation_confirmed = true.
                  |
                  |---> back-references COMPLAINT    [legal_case.source_complaint -> complaint]
                  |---> back-references INSPECTION   [legal_case.source_inspection -> inspection]
                  |---> back-references FACILITY     [legal_case.violating_facility -> facility]
                  |
                  +---> AGENT DECISION LOG           [1:many, log.linked_record -> legal_case sys_id]
                          Legal Case Summary Agent decisions logged here.
```

### Relationship Summary (Plain Text)

1. **Complaint -> Facility**: A complaint is optionally linked to a regulated facility via `linked_facility` (Reference). Multiple complaints can point to the same facility. This relationship drives the facility's complaint frequency count and risk score recalculation.

2. **Complaint -> Environmental Snapshot**: One-to-one. When the Severity Fusion Agent classifies a complaint, it creates exactly one Environmental Snapshot that freezes the AQI and weather data used for the decision. The snapshot references back to the complaint via `parent_complaint`.

3. **Complaint -> Inspection**: One-to-one (within hackathon scope). When Flow Designer dispatches an inspector, it creates an Inspection record with `parent_complaint` pointing back to the originating complaint. The inspection inherits the facility reference and inspector assignment.

4. **Inspection -> Inspection Finding**: One-to-many. During on-site investigation, the inspector creates multiple findings (photos, measurements, observations) under a single inspection via `parent_inspection`.

5. **Inspection -> Legal Case**: One-to-one. When the inspector confirms a violation (`violation_confirmed` = true), the Legal Case Summary Agent auto-creates a Legal Case. The legal case back-references the complaint (`source_complaint`), inspection (`source_inspection`), and facility (`violating_facility`).

6. **Facility -> Risk Score**: The facility's `risk_score` (0-100) is recalculated by a Business Rule / Scheduled Job whenever a complaint is filed against it, an inspection closes, or its compliance report becomes overdue. Facilities with score >= 80 are flagged for priority inspection via `high_risk` = true.

7. **Agent Decision Log -> All Tables**: The Agent Decision Log uses a flexible `linked_table` + `linked_record` pattern (similar to ServiceNow's `sys_journal_field`) to link to any EcoSentinel record. This avoids creating separate log tables per entity and provides a single pane of glass for AI Control Tower.

---

> **Table Creation Order**: Create tables in this order to satisfy reference dependencies:
> 1. Facility (no dependencies)
> 2. Complaint (references Facility)
> 3. Inspection (references Complaint, Facility)
> 4. Inspection Finding (references Inspection)
> 5. Legal Case (references Complaint, Inspection, Facility)
> 6. Agent Decision Log (no hard references — uses string-based linking)
> 7. Environmental Snapshot (references Complaint)
