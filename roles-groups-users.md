### 1.2 — Citizen Access & Authentication Strategy

* **Role Required**: **None (Public Access)**
* **Intake Mechanism**: Citizens submit reports anonymously via a public-facing **Service Portal Record Producer**. They do **not** log in, and they are **not** provisioned with a `sys_user` record or any roles. This reduces portal licensing costs and encourages frictionless reporting.
* **Lightweight Authentication for Tracking**:
  1. Upon submission, a Client Script returns the unique auto-generated Complaint Number (e.g. `ES-20260731-0042`).
  2. To track status, the citizen visits the public "Track Incident" widget, inputting their **Complaint Number** and the **Citizen Email** provided during submission.
  3. A secure server-side Script Include (`EcoComplaintUtils.lookupComplaint()`) validates the pair and returns the status timeline without revealing any other database records.

# Section 4: Access Control List (ACL) Summary

To ensure security inside the scoped application, ACLs must be configured. These enforce record-level and field-level permissions.

| Table / Field | Operation | Role Required | Justification (UX Gap / Failure Mode Prevented) |
|---|---|---|---|
| `x_eco_complaint` | **Create** | Public (Public Role) | Citizens must be able to submit complaints via the Portal without logging in. |
| `x_eco_complaint` | **Read** | `x_eco.inspector` · `x_eco.officer` | Inspectors can read complaints in their queue. Officers can read all complaints. Citizens cannot read other citizens' complaints directly in the table. |
| `x_eco_complaint` | **Write** | `x_eco.officer` · `x_eco.admin` | Restricts standard field edits to back-office staff. Inspectors can only view but not edit intake details. |
| `x_eco_complaint.ai_severity` · `ai_confidence` · `ai_rationale` | **Write** | `x_eco.integration_user` · `x_eco.admin` | Only the FastAPI integration account or system administrators can write to the raw AI analysis fields. Prevents staff tampering. |
| `x_eco_complaint.override_severity` · `override_reason` | **Write** | `x_eco.officer` · `x_eco.admin` | Only compliance officers can override the AI classification. Gated at the database level so inspectors cannot modify severity. |
| `x_eco_facility` | **Create / Write** | `x_eco.officer` · `x_eco.admin` | Facility metadata (addresses, contacts, status) must only be managed by administrators or compliance officers. |
| `x_eco_facility.risk_score` | **Write** | System process only | Risk scores are calculated, not manually edited. Enforce with a write ACL that denies interactive users and allows only trusted server-side logic / admin repair scripts when explicitly needed. |
| `x_eco_inspection` | **Read** | `x_eco.inspector` (Condition) · `x_eco.officer` | **Record-level restriction**: An inspector can only read inspections where `assigned_to` = `javascript:gs.getUserID()`. Prevents snooping. |
| `x_eco_inspection` | **Write** | `x_eco.inspector` (Condition) | An inspector can only write to inspections assigned to them, and only when the state is Open/WIP. |
| `x_eco_legal_case` | **Read only** | `x_eco.officer` | Compliance Officers can view legal case status for enforcement coordination, but cannot edit legal proceedings, penalties, or case narrative. |
| `x_eco_legal_case` | **Read / Write** | `x_eco.legal_handler` · `x_eco.admin` | Restricts legal proceedings and penalty management to the legal team. Inspectors have no access to Legal Case records, not even read-only. |
| `x_eco_agent_log` | **Create** | `x_eco.integration_user` · `x_eco.admin` | Only the integration user (FastAPI) and platform processes can write to the audit logs. |
| `x_eco_agent_log` | **Read** | `x_eco.officer` · `x_eco.admin` | Compliance officers and admins use these logs in the AI Control Tower. Inspectors do not need access. |
| `x_eco_agent_log` | **Write / Delete** | Deny by ACL + before-rule abort | **Critical security control**: This log is append-only for normal operation. A before Business Rule aborts update/delete attempts, while ACLs deny interactive writes. Emergency admin repair, if ever needed, must be a documented break-glass procedure. |
| `x_eco_env_snapshot` | **Read** | `x_eco.officer` · `x_eco.admin` | Environmental snapshots are read-only audit records associated with complaints. |
| `x_eco_env_snapshot` | **Write / Delete** | Deny by ACL + before-rule abort | Snapshot records are immutable for normal operation. Use append-only correction records rather than editing historical snapshots. |

# Section 5: Integration Account Configuration Requirements

To ensure the FastAPI backend uses a secure, non-interactive connection:
1. **User Record**: Set `ecosentinel.api` user field `Web service access only` = **True**. This prevents the credentials from being used to log into the ServiceNow Standard UI or Service Portal.
2. **Authentication**: Prefer OAuth 2.0. Use Basic Authentication only for PDI/demo speed, with a strong rotated password and `Web service access only`.
3. **Table API Access**: The integration user has ACL permissions to call `GET` and `PATCH` on `x_eco_complaint`, and `POST` on `x_eco_env_snapshot` and `x_eco_agent_log`. It has no access to standard ITIL tables (`incident`, `change_request`, etc.).
